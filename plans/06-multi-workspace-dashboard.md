# Plan 06 — Multi-workspace model, sharing, and a projects dashboard

Goal: every user gets their own workspace (already true today, as the `/app` personal space) and can also be given access to other people's workspaces — including the current shared site, which becomes **the flagship workspace, owned by suij1997@gmail.com**. A new dashboard lists "yours" + "shared with you" and lets users create additional workspaces beyond their default personal one.

**Scope decisions (confirmed with user 2026-07-14):**
- Users can create multiple workspaces (not just one auto-personal one) — like Notion, "New workspace" whenever.
- Sharing within a workspace has two roles: **editor** and **viewer**.
- The current shared site (global docs/collections/boards/templates) is associated with **suij1997@gmail.com** as its owner going forward. Confirmed: no one else currently uses the site, so cutover needs no other editors seeded — flagship starts with exactly one member (the owner).
- **Lightweight link invites**: someone without an account can be handed a share link, type their email, and get **view-only** access immediately — no password, no full sign-up. That grant is provisional: it's tied to their email (not a real account) until they actually complete real sign-in (Google/GitHub/email magic-link, via the existing auth already built), at which point it resolves onto their real account and upgrades to whatever role the link/invite actually specified (editor or viewer). This keeps the account "footprint" (a real `users` row) from being created just because someone clicked a link.

This plan **supersedes Plan 05's Phase 1** (a standalone global email allowlist) — that mechanism is subsumed by per-workspace membership below: a bare account with zero workspace memberships just sees an empty dashboard, so there's no separate "who's allowed to even sign in" gate to build. Plan 05's Phase 2 (swap `SITE_PASSWORD` for real sessions) is still required and is folded in as Phase 1 here. Plan 05's Phases 3-5 (profile icon, account page, billing scaffold) are unaffected and still apply once this lands.

## Phase 0 — Current state relevant to this change (confirmed 2026-07-14, do not re-derive)

The codebase already has the *exact* scoping pattern this plan generalizes — it just applies to one hardcoded axis (`userId`) instead of an arbitrary `workspaceId`:

- **Content storage** (`src/lib/store/paths.ts`): `dataFile(collection)` → legacy global `content.json`; `userDataFile(userId, collection)` → per-user `content.json` under `DATA_DIR/users/{userId}/{collection}/`. `src/lib/docs/store.ts`'s `readDocs`/`writeDocs` take an optional `{ userId }` scope and pick the file accordingly. Collections/templates/boards stores presumably follow the same shape (check each before assuming).
- **Live collab rooms** (`server/collab-core.ts`): each editable page is one Yjs room. Room name is either a bare `docId` (legacy/global) or `user:{userId}:{docId}` (personal space), parsed by `ROOM_RE = /^user:([^:]+):(.+)$/` (`parseRoom`, line 55-60). The WS upgrade handler branches on this to gate personal rooms by session + exact `userId` match (line ~206-247), vs. the legacy room's site-password gate (line ~254+).
- **This existing split is the template for workspaces** — a workspace is really just a named, shareable scope that content-files and room-names key off of, the same way `userId` already does for personal spaces.

### Why the migration can be additive (no data rewrite, no LevelDB risk)
Renaming existing rooms or content files is the risky part of this change (LevelDB is keyed by room name; get it wrong and live CRDT state silently orphans). This plan avoids that entirely by keeping every **existing** room/file naming scheme untouched and only introducing new identifiers for **new** workspaces:
- The **flagship workspace** (today's global site) keeps using bare `docId` rooms and the legacy `dataFile()` — internally it's "the workspace with no room prefix," recognized by convention, not renamed.
- Each user's existing **personal workspace** keeps using `user:{userId}:{docId}` rooms and `userDataFile(userId, ...)` — internally it's "the workspace whose id is `personal:{userId}`," again by convention, not renamed.
- Brand-new **custom workspaces** (Phase 4 below) get a fresh generalized scheme: `ws:{workspaceId}:{docId}` rooms and `workspaceDataFile(workspaceId, collection)` files — this new scheme is only ever used for workspaces created after this ships.

So `parseRoom`/`resolveFile` gain a third case, they don't lose or rewrite the first two.

## Phase 4 — Dashboard + workspace creation + sharing UI

**Implement**
1. Dashboard route: new path, **`/dashboard`** (confirmed separate from `/app` — `/app` keeps meaning "your personal workspace specifically"; `/dashboard` is the entry point that lists every workspace and links into each one, including `/app`). Two sections, "Your workspaces" (owned — flagship if applicable, personal, any custom ones) and "Shared with you" (member rows where you're not the owner), each workspace as a card linking into it. Add a "Dashboard" / "All projects" link from both `PersonalSidebarNav` and `SidebarNav` so it's reachable from anywhere, not just as a landing page.
2. "New workspace" flow: name prompt → creates a `kind: 'custom'` row owned by the current user.
3. Routing: generalize `/app/docs/[id]` into `/w/[workspaceId]/docs/[id]` (or similar), resolving `workspaceId` → scope via Phase 2's `canAccess` before rendering; redirect legacy `/docs/[id]` and `/app/docs/[id]` URLs to their canonical `/w/...` form for a transition period rather than breaking existing bookmarks/links.
4. **Sharing UI, two paths**:
   - **Direct member add** (owner-only, for people who already have accounts): add by email + role (editor/viewer) — if a `users` row exists for that email, create a resolved `workspace_members` row immediately; if not, fall through to the pending-grant path below (same mechanism the link flow uses) rather than silently failing.
   - **Shareable link** (the "let them view with the link once they provide an email" flow): owner generates a `workspace_invite_links` row (token + role) from the Share panel, gets a copyable `/invite/{token}` URL to send out-of-band (Slack, email, whatever — sending it is not this app's job).
     - Visitor opens `/invite/{token}` while signed out: page validates the token (404/expired message if revoked or unknown), then asks for an email (no password, no OAuth prompt).
     - On submit: server upserts a **pending** `workspace_members` row (`userId: null, inviteEmail: <email>, role: <link's role>`), and sets a signed, httpOnly cookie recording `{ workspaceId, email }` for this browser — signed the same way the legacy `AUTH_COOKIE`/`sessionToken()` pattern in `src/lib/auth/session.ts` was (HMAC over a server secret), **not** a raw client-supplied value, so a visitor can't just set an arbitrary email in a cookie and impersonate someone else's pending grant.
     - Subsequent page loads in that browser: `canAccess` middleware checks a real NextAuth session first; if none, falls back to `canViewByEmail` using the signed cookie — grants **view-only**, regardless of the role stored on the pending row (that stored role is what it becomes once resolved, per Phase 2.4).
     - When that email later completes real sign-in (any provider), `src/auth.ts`'s `createUser`/`signIn` callback resolves the pending row (`userId` gets set, `inviteEmail` match becomes moot) — access upgrades in place to the link's actual role (editor or viewer), now durable and cross-device, and the workspace shows up under that account's "Shared with you." **This is the "full setup"** the user described — no full account exists until this step.
     - Known simplification, worth calling out rather than silently accepting: the email step doesn't verify the visitor actually owns that email (no confirmation link sent) — the invite **token** is the real secret here, email is bookkeeping so the grant reattaches to the right account later. Anyone holding the link could type someone else's email and squat on their eventual grant. Low-stakes for a small/trusted-recipient use case; flag if this needs hardening later (e.g. require the confirmation click before persisting the pending row).

**Verify**: sign in as two different test accounts; owner shares a custom workspace with the second account as viewer, confirm the second account sees it under "Shared with you," can view but not edit; promote to editor, confirm edit access now works. Separately: generate an invite link as a signed-out visitor (fresh browser/incognito), confirm email-gate view access works pre-account, then complete real sign-in with that same email and confirm the workspace now appears in that account's dashboard with the link's actual role.

Real access enforcement still happens at the page/layout level.
- **Bug found and fixed during QA**: `(workspaces)/layout.tsx` — the shared `<html>`/`<body>` shell wrapping *both* `/dashboard` and `/w/[workspaceId]/*` — had its own unconditional `if (!session?.user) redirect('/app/login')` predating this feature. Fixed by removing the gate from the shared shell (now purely a shell, no auth logic) and adding an equivalent explicit check to `/dashboard/page.tsx` (which has no cookie-fallback concept and still needs a real session) — `/w/[workspaceId]/layout.tsx` already had its own complete gate and needed no change.
